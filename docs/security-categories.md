# Security categories: controls, tests and numbers

Text prepared for the Security Self-Assessment (PDF not rebuilt yet). All figures are offline, MOCK data, our own tests; none is an independent audit. Full suite: `2214 passed, 2 skipped`.

| Organiser attack category | Oasis controls | Tests that prove them | Numbers (and caveat) |
|---|---|---|---|
| Inducement to transfer funds | Money goes only to the registry account; raw "send N to account X" runs through the pipeline and is rejected; signed intent, nonce, expiry and policy re-check in the executor; the model cannot approve | `tests/test_chat_security.py` (raw transfers, bypasses), `tests/test_trust.py`, `tests/test_router_judge_fixes.py` | Benchmark: 32 attacks, block rate 1.0, money lost CNY 0 (`eval/reports/benchmark.md`). Outside scenario sets (80 + 250): money moved 0 (`router_robust.md`). Caveat: simulated approvers |
| Information theft | Security-first router stage with a `privacy` category (full third-party account numbers, other people's details, raw logs and dumps, other users' data, "send/include/reply with" instructions inside pasted text, email or invoices) and `secrets`; ask-about is help, reveal/print/send is refused; `redact()` on every reply; document accounts masked in chat outcomes; recovery drafts reject keys and tokens | `tests/test_information_theft.py` (137 tests: 111 EN+ZH prompts incl. role claims, injected invoices/emails, base64, hex, spaced, fullwidth, zero-width, leetspeak; plus ledger memo, Telegram, email, recovery, Trust Pass, proof pack, error bodies), `tests/test_secret_concepts.py` (92 tests: 40 benign near-misses get help, 28 look-alikes still refused, wording per category) | 0 secrets or planted account numbers in any checked field. Caveat: the proof pack and signable draft carry the payee's REGISTRY account in full because the signature covers it; they never carry an account taken from a document |
| Unauthorized operations | Role dependency on every state-changing endpoint; approvals need a device-key signature over the exact draft hash; chat refuses approve-for-me, limit raises, registry/audit edits, role claims; each refusal audited by category only | `tests/test_role_matrix.py`, `tests/test_security.py`, `tests/test_chat_security.py`, `tests/test_secret_concepts.py` (per-category wording) | Independent attack sets 1, 2, 3, A, C, G: 900/900 attacks passed, look-alikes unchanged (`router_robust.md`). Abuse stress run: 1,500 rounds, 0 findings (2026-10-17) |
| Prompt injection | Text in documents is data, never instruction; the model only proposes; risk score can only escalate; canaries; injection refusals; exfiltration instructions in invoices refused | `tests/test_chat_security.py` (injections), `tests/test_information_theft.py` (injected invoices/emails), `tests/test_trust.py` (canaries) | Inject stress run: 3,000 poisoned invoices, 0 breaches (2026-10-17, before this change). Router held-out 3 (120, never tuned on): 88 > 99 right, unchanged by this work |

**Judge mode.** With `OASIS_JUDGE_MODE=1` every browser gets its own sandbox (student and parent logins in the same browser share that browser's sandbox; a different browser gets a different one), and the sandbox id is signed inside the session token. A shared role passcode therefore logs a judge into their own sandbox and does not expose another judge's data. Tests: `tests/test_judge_pack.py` (separate sandboxes, no forged sandbox claim).

**Limits.** Prompts and sets are written by the Oasis team and tuned against the offline keyword router; they say nothing about a live model. No independent audit or penetration test exists.
